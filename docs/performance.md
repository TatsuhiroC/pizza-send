# 传输性能与测量

文件协议使用最多 32 KiB 的网络数据块，以接收端已写入的进度确认。发送窗口随反馈调节，并独立限制浏览器发送缓冲和接收队列；有在途数据不代表已经落盘。接收端合并短写入，但不能延迟应当发出的回执，也不能跨文件或压缩块混合边界。

增量 SHA-256 覆盖原文件全部字节。接收端优先使用 WebAssembly，失败时回退到 JavaScript；不以整文件读入换取加速。源文件校验只读取有界头尾片段，最多四份文件并行，不提前读取完整的大文件。慢网压缩是独立的按需建议，见[触发公式](transfer-compression.md)。

## 可复现的基准

`tests/performance/` 保留当前代码可运行的传输和延迟回执基准，默认回归不运行它们：

```sh
npm run bench:transfer
BENCH_MIB=32 BENCH_REPEATS=1 BENCH_DELAYS=0,150 npm run bench:latency
```

需要比较发布构建时，先构建候选，将另一个版本的产物放在独立目录，再通过 `BENCH_BUILT=1` 和 `BENCH_BASELINE_DIST` 指定对照。`BENCHMARK_RESULT` 指向仓库外或被忽略的 `test-results/` 路径，不把每轮 JSON 提交到仓库。

基准检查下载原名和独立 SHA-256，能记录阶段耗时、读写和在途窗口。本机 DataChannel、模拟慢读取或延迟 ACK 不等于真实公网；裸通道速度不等于完整文件传输速度。

## 解释结果

同一 Wi-Fi、跨 Wi-Fi、5G、VPN 和服务器转发使用的路径不同。WebRTC 成功连通不保证吞吐，视频会议允许降清晰度和丢弃过期帧，文件传输必须完整可靠。

优化应使用同一设备、文件、路径和交替重复的前后对照，区分初次配对、传输、校验及系统保存。遇到真实慢传，先使用[连接诊断](connection-diagnostics.md)记录路径、排队与确认进度，不用另一时间的历史数字代替根因。当前没有保证任意网络可达到固定 MB/s。
