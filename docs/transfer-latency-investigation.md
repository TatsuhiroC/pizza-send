# 延迟回执时的速度回退复核 · 2026-10-16

本页为修订前的诊断记录；后续实现与同条件对照见[自动窗口修订](transfer-adaptive-control.md)。

结论：本地候选 `10fe0d7` 存在可复现的速度回退，不能按“全面提速、没有代价”发布。线上基线为 `b25e218`。本轮只增加测试与记录，没有修改生产传输代码、推送提交或部署。

## 复测方式与结果

同一台 Mac、Chrome、本地真实 WebRTC DataChannel 和 OPFS。旧版从 Git 提取独立快照，使用与候选版相同的基准脚本、配对服务、文件内容与计时。32 MiB 每轮交替测试 150、0、300 ms，下一轮反转顺序；128 MiB 反向先跑候选、再跑旧版。各组 3 次，以下为中位数。版本之间没有逐次随机交错，不能消除所有机器负载、浏览器和缓存差异。

| 文件 | 额外应用回执延迟 | 旧版 | 候选 | 耗时变化 |
| --- | ---: | ---: | ---: | ---: |
| 32 MiB | 0 ms | 3.357 秒 | 1.503 秒 | 减少 55.2% |
| 32 MiB | 150 ms | 1.334 秒 | 1.675 秒 | 增加 25.6% |
| 32 MiB | 300 ms | 2.512 秒 | 2.809 秒 | 增加 11.8% |
| 128 MiB | 150 ms | 5.373 秒 | 6.328 秒 | 增加 17.8% |

计时从接收方发出 `accept` 到发出 `complete`，包含接收、写盘、完整性校验和完成处理，不含页面启动、选文件、连接建立及下载后独立校验。150/300 ms 只在测试程序中推迟自动回执发送，不需要人工点击，也没有放进生产代码。它不是完整的真实广域网延迟、带宽或丢包模拟，不能直接推导真实手机或跨地区速度。

旧版 32 MiB／150 ms 的三个结果为 3.893、1.331、1.334 秒，波动很大；因此之前的 21.3% 不是稳定的普适比例。不过 128 MiB 对照更集中：旧版 5.359–5.459 秒，候选 6.299–6.418 秒。这表明回退不能仅解释成短文件的偶然噪声，也不能据此声称真实网络都会慢 18%。

## 诊断证据

主要问题在发送调度与应用流控的配合。生产代码中的自动写入回执必须保留，它决定已提交字节和续传位置；本轮没有删除回执或提前确认未写入数据。

1. 候选 32 MiB／150 ms 每次有约 487–525 次被归为节奏等待的检查失败；完成的短定时等待累计约 0.80–0.89 秒。这些是等待与唤醒的计数，不能直接等同于删除它们后可节省的端到端时间。
2. 候选起始窗口为 2 MiB，旧版固定上限为 4 MiB。在一组轨迹中，候选发送到 2 MiB 后到 3 MiB 的时间从约 114 ms 跳到 227 ms；旧版分别约 66 ms、98 ms。较小起始窗口遇到延迟回执，会较早等待接收反馈。该轨迹说明启动行为差异，并没有单独量化窗口对总耗时的贡献。
3. 仅在浏览器隔离测试中禁用节奏等待、保留自适应窗口：150 ms 场景中位数从 1.675 降到 1.512 秒；普通本地场景却从 1.503 升到 4.200 秒，发送缓冲等待和 250 ms 兜底唤醒增多。直接取消 pacing 无法作为修复。
4. 仅在测试中将节奏批量从 64 KiB 放宽至 256 KiB：150 ms 场景为 1.533 秒，普通场景为 5.435 秒。简单扩大突发量同样不能作为修复。诊断组其中一次运行期间执行了约半秒的本地构建，因此这组只作为定性排错证据；其余两次普通场景仍分别为 5.612、5.055 秒。
5. 同时采用无 pacing、固定 4 MiB 窗口、固定 1 MiB 浏览器缓冲目标，保留新流水线：150 ms 场景为 4.365 秒。这个组合同时改变了多个变量，不能拿来单独归因于窗口；它也表明“套回旧窗口参数”不是已验证的解决方案。

上述对照没有单独关闭接收批量写盘，不能据此声称写盘批量大小完全不影响性能。但写盘 RPC 显著减少，且改变发送策略即可改变回退，当前应优先修订发送调度；尚未定位到浏览器原生传输栈内部的具体原因。

## 后续修复应满足的条件

- 保留有界预读、原始消息大小限制、接收队列保护、确认后续传和最终 SHA-256 校验。
- 调整发送节奏与窗口增长的配合，减少高吞吐时的频繁短等待，同时避免重新形成长时间的发送缓冲阻塞；不能只删除限速或一律扩大突发量。
- 使用相同夹具重新对照普通、延迟回执、慢接收方、较大文件；候选不能只在一个速度场景变快。
- 代码调整后重跑相应的断线恢复、取消、磁盘失败、多人分享及完整性回归。实机 iPhone、VPN、跨地区网络仍需另外验证。

本轮共 **42 次成功传输**，每次检查原文件名、下载后独立 SHA-256 和不超过 4 MiB 的未确认数据上限；并非 42 项新的产品功能。128 MiB 夹具首次因 Playwright 的内存输入上限失败，未开始传输，改为真实磁盘文件后 3 次全部通过，不计入成功次数。生产构建通过，输出脚本仍为 `index-E73PEyQu.js`，与候选原构建一致。没有修改生产源码，因此没有重复整套 180 项功能回归。

每次计时、队列峰值及等待计数见[统计记录](archive/benchmarks/2026-10-16-latency-review.json)。完整逐 MiB 轨迹另存于本机 `outputs/pizza-send-throughput-verification/latency-review/`。

## 复现

```sh
# 默认：32 MiB，各延迟 3 次，normal 模式不替换候选流控方法。
BENCHMARK_RESULT=/tmp/pizzasend-latency.json npm run bench:latency

# 128 MiB：当前夹具已对所有大小统一使用真实磁盘文件。
BENCH_MIB=128 BENCH_DELAYS=150 BENCHMARK_RESULT=/tmp/pizzasend-latency-128.json npm run bench:latency
```

可用诊断变量：`BENCH_MODE=unpaced`、`burst256`、`fixed`，仅由测试脚本在隔离浏览器中替换实例方法；这些策略不进入产品构建。`BENCH_VARIANT` 只是输出标签，不选择生产代码。旧版对照需另行检出 `b25e218`，复制同一基准脚本、夹具及基准配置，共用同版本依赖，然后顺序运行，避免同时竞争端口、CPU 和磁盘。
