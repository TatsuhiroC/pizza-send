# 读写流水线与自适应发送 · 2026-10-16

本页保留首轮候选 `10fe0d7` 的历史实现与测量，**不是当前实现说明**。该方案经[回退复核](transfer-latency-investigation.md)后未发布；后续已移除大块预读与额外定时限速，改为按写入回执调整窗口，详见[当前控制逻辑与对照结果](transfer-adaptive-control.md)。

## 实现与边界

- 发送端按 1 MiB 读取，最多保留当前块和一个预读块；网络消息仍最多 32 KiB，并遵守对端的消息大小限制。取消、重连后的旧预读结果不能发送；弃用的预读失败不会产生未处理的 Promise 拒绝。
- 接收端将相邻数据合并为最多 256 KiB 的写盘请求，低流量时安排 4 ms 后提交，实际时间受浏览器调度影响。文件控制消息到来前先提交尾块，避免跨文件合并；替换连接前等待旧批次写完，再报告续传位置。取消会丢弃尚未提交的尾块。
- SHA-256 仍按原始字节增量计算，只有成功写入后才累计接收字节并确认。部分写入失败不确认、不提供损坏下载；最终文件完成确认仍在写盘关闭及整文件校验之后。
- 发送窗口从 2 MiB 起步，在 512 KiB 至 4 MiB 之间调整；浏览器发送队列目标在 512 KiB 至 1 MiB 之间。网络原始消息大小、8 MiB 接收队列保护、4096 条排队消息保护均保留。单个新增接收合并缓冲最多 256 KiB，不随文件总大小增长。
- 控制器使用累计确认吞吐、确认等待时间和拥塞迹象。确认等待包含网络、浏览器排队和接收方写盘时间，并非纯网络 RTT。首次确认不用于吞吐估计，避免把建立初始反馈所需的时间算作稳定带宽。
- 64 KiB 令牌桶限制连续发送突发，按已确认吞吐探测可用速率；每发送约 128 KiB 交回浏览器任务调度，让确认、写盘回复和页面交互运行。短 pacing 等待与原有 250 ms 超时兜底区分，恢复期间维持低频等待，避免持续高频唤醒。
- 不新增第三方依赖、服务器、文件压缩或有损处理。未改变协议版本、文件元数据、续传偏移校验和最终摘要校验。

## 对照结果

本机 Chrome、相同 32 MiB 文件、真实本地 WebRTC DataChannel 与 OPFS 写盘，每场景各运行三次，取中位数。旧版基线为 `b25e218`。主要计时从接收端发出接收确认到发出完整传输确认，包含校验、写盘及完成处理；浏览器初始化和独立下载后校验不计入该数值。测试同时保留从点击接收到界面完成的墙钟时间，不能混用两种计时。

| 场景 | 旧版传输时间 | 本次传输时间 | 时间变化 |
| --- | ---: | ---: | ---: |
| 普通本地传输 | 3.806 秒 | 1.538 秒 | 减少 59.6% |
| 每次文件读取额外延迟 2 ms | 4.050 秒 | 1.524 秒 | 减少 62.4% |
| 每个应用确认额外延迟 150 ms | 1.420 秒 | 1.723 秒 | 增加 21.3% |

32 MiB 文件的发送文件读取从 1024 次降到 32 次；普通场景接收写盘请求中位数从 1024 次降到 187 次。每次输出均再次下载原文件并以独立 SHA-256 核对，未使用压缩。

**不能据此承诺所有网络提速。** 读取延迟和确认延迟均由隔离浏览器注入，150 ms 应用确认延迟不是实际 WAN 的完整延迟、丢包与带宽模型。高吞吐延迟确认场景存在约 0.303 秒、21.3% 的回退，已保留原始结果。真实 iPhone、Wi-Fi、VPN 和跨地区效果仍需实机对照。大文件功能验证通过也不等于所有大文件都有表中的提速倍数。

原始数据：[旧版](../benchmarks/results/2026-10-16-before.json)、[本次](../benchmarks/results/2026-10-16-after.json)。

## 复现与正确性验证

```sh
BENCHMARK_RESULT=/tmp/pizzasend-benchmark.json npm run bench:transfer
```

基准单独运行，避免与其他测试同时争用 CPU 和磁盘；默认 CI 不将硬件相关的速度数值作为通过阈值。基线复测需使用同一基准脚本与旧版生产传输代码，保持浏览器、文件、数据路径和计时定义一致。

新增专项覆盖：有界预读、取消及异步失败、恢复后清除旧确认计时、慢接收方的窗口缩小与恢复、原消息及合并写入大小上限、奇数长度尾块、文件边界、断线时的未提交尾块、取消清理、恢复时避免短间隔忙等。

Chromium 实际传输执行多次重连、多人独立传输、整文件摘要、原文件保存、磁盘部分写入失败，以及 200 MiB、1 GiB、512 MiB 流式落盘回归。WebKit 执行批量接收状态与保存、界面、常亮专项；真实 WebKit WebRTC 传输仍不纳入自动化通过项。最终构建另检查现有 CSP 等安全策略。

旧磁盘故障夹具只在恰好第二个 32 KiB 调用处抛错，批量写盘后不再触发。已改为在 32 KiB 字节边界模拟部分系统写入，再抛出磁盘满，并断言没有未提交字节的确认及损坏下载。

最终本地结果：Chromium 完整回归 149 项通过；WebKit 22 项通过、3 项有意跳过；构建安全策略 9 项通过、1 项有意跳过。合计 180 项通过、4 项有意跳过。构建及配对服务 dry-run 检查通过，没有部署服务。速度对照的 9 个场景运行不重复计入功能检查总数。
