# 自动窗口与自适应写盘 · 2026-10-16

> 本文保留 `8c36fac` 阶段的历史结果。后续发布构建交替对照、接收端校验加速及其兼容成本见 [2026-10-17 复核](transfer-receive-hash.md)。

本轮用更简单的应用流控替代首轮候选的大块预读和定时限速。改动保持本地，未推送或部署；线上基线为 `b25e218`，上一候选为 `10fe0d7`。

## 当前自动控制

- 浏览器继续负责 WebRTC/SCTP 的网络拥塞控制。应用根据**实际成功写入后的累计回执**估计吞吐与反馈等待时间，自动调节未确认数据窗口，不再叠加按固定时间补充额度的发送限速器。
- 窗口起始 4 MiB，硬边界 512 KiB–4 MiB。稳定、较慢的反馈保留足够发送余量；快速反馈可以缩小未确认量。持续出现比历史基准更长的等待，同时回执停顿或吞吐下降，才按拥塞迹象收紧。根据约 100 ms 的吞吐样本平滑估计目标，遇到窗口限制后逐步恢复。反馈时间包含浏览器排队、传输和接收端写盘，不是纯网络 RTT。
- 正常发送使用最多 32 KiB 的顺序读取与网络消息，读取后检查长度及取消／连接代次，继续保留原始字节 SHA-256 和续传检查点；必要的续传前缀重算仍沿用原有 1 MiB 读取。浏览器发送队列目标最多 1 MiB；队列阻塞时依靠事件及 8 ms 兜底检查，单纯等回执使用 250 ms 兜底；恢复期间始终使用低频 250 ms 等待。健康发送没有额外的固定定时限速。
- 接收端根据到达密度选写盘批次：相邻数据密集时合并，单批最多 256 KiB，并安排 4 ms 尾批提交；若两次数据到达间隔至少 1 ms，当前批次及时提交。实际计时精度及唤醒时间受浏览器影响。
- 批次也在累计 256 KiB 回执边界提交，避免若干短批次不断把下次回执推迟。只有写盘成功才增加提交字节、发回执；到达文件末尾再确认。多文件、奇数尾块、断线前尾批次与整文件校验均保留。
- 连接重建、发送页或接收页从后台返回时，发送端清除旧吞吐和反馈时钟，重新估计；已提交字节、文件校验状态及续传进度不因此重置。
- 原始单消息 64 KiB 接收保护、8 MiB／4096 消息接收排队保护不变；未确认量最多 4 MiB。密钥、DTLS、信令协议和文件内容均未改变。没有新依赖、文件压缩、服务器或服务费用。

删除了不再使用的 `file-blocks.ts`、`browser-turn.ts` 和对应预读／令牌测试，用窗口反馈、短读取、稀疏写入、回执边界及恢复检查代替。首轮的“读取调用从 1024 降到 32”已不适用于当前版本；更少的读取次数并未稳定换来更好的总耗时。

## 同条件三版本对照

同一台 Mac、Chrome、真实本地 WebRTC DataChannel、OPFS，**所有大小均通过实际磁盘文件路径选择**。每组 3 次，中位数如下。主要计时从接收方发出 `accept` 到发出 `complete`，包含写入、校验和完成处理，排除页面初始化、连接建立及下载后独立 SHA-256 校验。

| 文件／额外应用回执延迟 | 线上旧版 | 上一候选 | 本轮修订 |
| --- | ---: | ---: | ---: |
| 32 MiB／0 ms | 1.370 秒 | 1.517 秒 | 1.358 秒 |
| 32 MiB／150 ms | 1.360 秒 | 1.627 秒 | 1.354 秒 |
| 32 MiB／300 ms | 2.462 秒 | 2.817 秒 | 2.430 秒 |
| 128 MiB／150 ms | 5.502 秒 | 6.081 秒 | 5.391 秒 |

本轮相较上一候选约减少 10.5%、16.8%、13.7%、11.4% 的耗时；与线上旧版整体接近。几％差异不足以承诺真实设备的固定提速，测试没有逐次随机交错，仍有机器负载与运行顺序等影响。128 MiB 本轮三次为 5.349、5.391、5.823 秒，旧版为 5.451、5.502、5.604 秒，必须连同范围判断，不能只挑最快一次。

32 MiB 普通场景本轮写盘请求中位数 980 次、旧版 1024 次；128 MiB 延迟回执场景为 3938 次、旧版 4096 次。这些流本来较稀疏，所以主动减少合并等待，而不是追求最少 API 调用。密集到达时能够合并的行为由专项测试另行检查，不能把首轮的巨大写盘调用降幅套用到所有网络。

**本轮结论是消除候选的明显回退，并保留自动背压，而非“所有场景全面加速”。** 先前 32 MiB 测试用工具注入的内存文件，本轮统一为实际磁盘文件，不能拿旧表的 3.8 秒与此表混算出两倍提速。所有旧结果仍保留在[首轮记录](transfer-performance.md)及[回退复核](transfer-latency-investigation.md)。150／300 ms 只是测试里推迟自动回执，不是人工确认，也不是完整的真实 WAN 延迟、带宽、丢包模型；不代表实机 iPhone、VPN 或跨地区测量。

最终对照共 36 次成功传输，逐次下载并检查原文件名及独立 SHA-256，同时断言最多 4 MiB 未确认量。各次计时、等待与队列计数见[对照记录](archive/benchmarks/2026-10-16-adaptive-control.json)。完整逐 MiB 轨迹及被弃用的实验留在本机 `outputs/pizza-send-throughput-verification/adaptive-retune/`，没有进入产品构建。

## 验证与复现

```sh
BENCHMARK_RESULT=/tmp/pizzasend-latency.json npm run bench:latency
BENCH_MIB=128 BENCH_DELAYS=150 BENCHMARK_RESULT=/tmp/pizzasend-latency-128.json npm run bench:latency
```

`bench:latency` 与旧 `bench:transfer` 使用独立匹配配置，避免同一输出文件被两套基准的结束钩子覆盖。默认 CI 不运行硬件相关的速度基准，也不把速度值当成功能阈值。旧版对照需独立检出相应提交，复制相同的基准脚本、夹具与配置，共用同版本依赖，然后顺序运行；`BENCH_VARIANT` 只是记录标签，不选择生产代码。旧版没有 `bench:latency` 脚本时，可使用旧提交自带的配置；当前仓库统一运行 `npm run bench:latency`，专用配置位于 `tests/config/`。

新增确定性覆盖稳定延迟与拥塞的区分、持续反馈恢复后的窗口增长、重置旧时钟、稀疏到达不等批次定时器、短批次不漂移回执及异常短读取不发送数据。真实传输另检查慢写盘、原文件下载、队列／消息上限，并重跑后台返回、多人独立传输、连接重建、磁盘失败、较大文件和 CSP 等原有检查。

最终本地验证：Chromium 完整回归 **152 项通过**；WebKit **25 项通过、3 项按设计跳过**；构建安全策略 **9 项通过、1 项按设计跳过**。合计 **186 项通过、4 项跳过**，跳过项均涉及当前独立 WebKit 自动化不覆盖的真实 WebRTC 传输场景，不能解读成已完成真机 iPhone Safari 验证。构建、配对服务 dry-run、两套基准独立匹配检查通过。36 次对照传输不重复计入功能检查总数。

200 MiB、1 GiB、512 MiB 的流式落盘及独立文件校验均通过；1 GiB 本机功能检查用时约 60.48 秒，包含独立读回校验，不是广域网速度对照。最终主脚本 gzip 为 61.90 kB，未新增依赖。测试结束后没有代码变更、推送或部署。

检查产物位于本机 `/tmp/pizzasend-adaptive-full`、`/tmp/pizzasend-adaptive-webkit` 与 `/tmp/pizzasend-adaptive-headers`。
