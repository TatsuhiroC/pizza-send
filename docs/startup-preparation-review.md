# 创建准备优化与全仓审查 · 2026-10-24

基于已发布主分支 `645215d`。维护者授权加入连接预热、预检缓存和多文件并行检查，完成审查与验证后提交、合并并发布网页和配对 Worker。

## 三项优化

1. **连接预热**：配置就绪后，为实际选用的 HTTPS 配对服务添加一个匿名 `preconnect` 提示，让浏览器有机会提前处理 DNS、TCP 和 TLS。用户改服务时替换提示；手动配对、不安全地址和同源地址不添加。不请求健康接口，不提前创建房间，不发送邀请密钥或文件信息。提示是浏览器尽力处理的优化，不保证消除首次建连耗时，也不会预热房间创建的数据库操作。
2. **预检缓存**：只有通过来源检查的成功 `OPTIONS` 返回 `Access-Control-Max-Age: 600`。浏览器可在匹配的网址、请求方法和请求头范围内复用十分钟的跨域许可；新房间地址通常仍需要首次预检。房间正文、票据、认证结果和文件不因此缓存，业务响应继续 `no-store`。每次实际请求仍执行来源、凭据和限流检查。
3. **有界并行检查**：创建前最多同时检查四个文件；每个文件仍先读开头最多 32 KiB，再读结尾最多 32 KiB。没有整文件预读或并行启动多个传输循环。四路读取的单次请求正文合计最多 128 KiB，这不是整个浏览器的内存上限。首个错误保留原文件名与可操作提示，并取消其他应用等待；取消或旧操作迟到不会继续检查新文件。保留原有十五秒单次读取截止。

原生 `Blob.arrayBuffer()` 不能真正取消；应用停止等待后，底层文件提供者可能继续读取。四路比一路会有更多同时发生的 I/O，采用小窗口限制这一代价，而不是无限并发。

## 实测与边界

同一隔离 Chrome、同一批生成在本地磁盘的文件，新旧各六次交替测量，均只检查首尾，内容与总读取字节核对一致：

| 场景 | 原版中位数 | 新版中位数 |
| --- | ---: | ---: |
| 单个本地文件 | 0.55 ms | 0.55 ms |
| 32 个本地文件 | 18.95 ms | 9.20 ms |
| 32 个文件，每次读取额外模拟 5 ms 等待 | 463.30 ms | 133.80 ms |

第三行是受控延迟实验，不是手机实测。32 个文件总计检查 2 MiB，观测到最多四次读取同时进行。测量存在系统缓存和调度波动，不代表公网吞吐或每次创建都能按此比例加速。

原生浏览器缓存测试使用没有网络拦截的独立环境：第一次请求产生预检，超过旧版默认五秒后仍能复用；错误凭据依然返回 401，服务端撤销来源许可后依然返回 403，实际业务响应仍为 `no-store`。没有用前端模拟的成功响应冒充浏览器缓存效果。

## 审查结论

重新检查全部自有生产模块与配对 Worker，重点覆盖创建与取消顺序、密钥派生和加密协商、票据及房间所有权、限流、接收队列和解压边界、文件散列与断点、OPFS 暂存和清理、系统保存、目录打包、扫码与页面生命周期。同时复核样式与本地预览入口、构建输出、安全头、依赖锁文件和持续集成；第三方依赖检查已知漏洞与使用边界，没有逐行审计全部第三方源码。

- 没有发现新的创建死循环、认证绕过或文件泄露路径。创建前的循环会推进文件索引；网络恢复和读取等待均有暂停、退出或截止条件。既有网络往返和房间存储等待仍然存在，不能将它们全部消除。
- 没有发现可以确定删除的废弃生产模块。严格未使用符号检查通过；无占位符的翻译键均找到源码引用，动态错误翻译保留。手动配对、旧格式邀请、散列与保存回退、本地设计预览和历史实验仍有用途，不做推测性删除。
- 两个本地预览入口、测试和实验不进入正式构建。默认 Worker 入口和公共预览入口继续关闭；不创建测试域名。
- 依赖锁定与现有 Undici 修补覆盖保持有效，生产及开发依赖的 `npm audit` 已知漏洞均为零。
- `main.ts` 与 `protocol.ts` 仍较集中；后续可按保存界面、配对流程、传输状态拆分。当前没有证据表明仅拆文件能缩短等待，因此不在此次优化中大规模重写。

审查还修正了安全测试辅助代码的请求头合并：原来大小写不同的 `Origin` 可能被拼接成两个值，现在按 HTTP 请求头规则覆盖，避免来源限制测试因错误输入而碰巧通过。安全专项加入 WebKit 回归；真实 WebRTC 场景由 Chromium 执行，不计为 WebKit 通过。

## 发布与验证

本地检查涵盖四路上限、完整首尾检查、坏源取消、用户取消、迟到结果、空文件及超过 4 GiB 的安全范围、配置与预热生命周期，以及缓存后的认证和来源限制。另执行严格构建、Worker 部署干跑、依赖扫描，并由合并请求运行完整 Chromium、WebKit 和生产安全头检查。最终通过数量与部署版本以 PR 检查和正式发布回执为准。

合入后由现有 Cloudflare Pages 发布前端；配对 Worker 需另行部署本次响应头变更。实际收发与正式资源版本需上线后再次核对。没有改变文件加密、慢网压缩的可选触发条件、免费服务限额、域名或 TURN 设置。
