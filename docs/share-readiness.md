# 分享链接与二维码显示延迟 · 2026-10-24

基于已发布主分支 `1f14c73`。本次修复已完成本地验证，并获维护者批准合并发布；前端随合入 `main` 更新。

## 原因与复现

创建分享成功后，发送端仍要读取成员状态、取得一次性票据、等待通知 WebSocket 握手，之后才填写链接并生成二维码。成员状态返回时已经触发界面回调，先显示了“等待接收方”；余下两次网络等待中，分享区域仍隐藏。这与用户截图中“等待状态已经出现，稍后链接和二维码才出现”一致。

这段先连接后展示的顺序早于最近的隐私清理。耗时会受网络影响，不能把这次观察直接归因于二维码计算退化或最近一次发布。原代码的回归用例在阻塞票据请求时失败：状态已经显示等待，分享区域却仍隐藏。

一次隔离 Chrome、390×844 视口、正式服务测量得到：

| 事件 | 距“正在创建传输” |
| --- | ---: |
| 创建房间响应 | 8,462 ms |
| 成员状态响应 | 9,378 ms |
| 显示等待 | 9,380 ms |
| 票据响应 | 9,902 ms |
| 通知 WebSocket 打开 | 13,867 ms |
| 链接与二维码显示 | 13,880 ms |

该次等待状态下的空白为 **4,500 ms**；握手完成后约 13 ms 就显示分享。它是一次具体网络下的样本，不代表用户的 1—1.5 秒会固定变成上述数值。

## 修复

房间创建响应通过既有校验后，在本机先准备好二维码，再同时显示二维码、链接和等待状态，然后继续建立成员通知连接。不在房间创建失败、限流或验证未完成时提前展示邀请；鉴权、凭据、消息限制与实际文件通道不变。

提前扫码可能让第一位接收者在通知连接尚未打开时就完成文件。此时初始文件连接会正常停止，因此后续归属判断检查当前分享组，不能把初始连接停止误判为用户已结束分享。

通知初始化最终失败时，清除已展示的链接和二维码，显示错误并允许重试。取消后旧请求晚返回，不能清除或替换新分享。二维码继续使用版本与链接双重检查，避免复用旧画布。

修复页面连接同一正式配对服务的另一次测量：创建响应为 7,872 ms，等待状态、链接和二维码均在 7,889 ms 显示，随后开始成员状态请求。测得的等待空白为 0 ms。两次创建请求本身耗时不同，因此不将总时间差宣传成稳定的性能提升，也不承诺点击创建后网络注册一定瞬间完成。

## 验证范围

新增回归覆盖成员请求与票据请求被阻塞时的实际二维码解码、失败清理与重试、取消后的旧回调隔离、提前加入后的原名与独立 SHA-256，以及首位接收者在通知握手前完成后，后续接收者继续使用同一邀请。

最终本地验证：生产构建与 TypeScript 检查通过；Chromium 32 项相关回归通过，包含六项新增用例、多人分享、连续两次实际二维码扫码、源文件失效、网络错误与旧结果隔离；独立 WebKit 四项就绪／失败／取消回归通过，两项真实 WebRTC 用例按既有引擎覆盖范围跳过，由 Chromium 执行。按用例与引擎去重，共 36 项通过、两项跳过。最初六项单独复跑没有重复计入。

以上为发布前验证，浏览器自动化不等于真实 iPhone 或特定运营商的实测。合并检查与正式部署结果以本次 PR 和发布核对为准。没有创建公网预览、修改 Worker、关闭安全检查或调整免费服务额度。
