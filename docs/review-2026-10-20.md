## 1. 选择保存位置与重连握手竞争，重复启动发送（P2）

接收方已经看到文件列表，系统保存位置选择框仍未返回时，网络可能触发重连。若选择框恰好在新数据通道打开后、重复文件列表到达前返回，旧逻辑会先发送 `accept`，随后又通过 `resume` 报告已经接受。发送方会启动两次相同文件的发送循环，破坏文件顺序或完整性校验。

修复后，接收方在恢复期间保留选好的文件句柄，通过下一次恢复快照报告接受状态；发送方在等待恢复快照时忽略提前到达的 `accept`，兼容旧接收页面。选择框在数据通道尚未打开时返回，也不会丢掉保存许可或向关闭的通道发送接受消息。界面继续显示恢复状态。

回归覆盖三种顺序：新通道打开但文件列表未到、通道尚未打开、旧接收页面先发 `accept`。另使用真实 WebRTC 重连、延迟发送重复文件列表，确认只启动一次文件发送、保留原保存位置，实际落盘内容与原文件一致。

## 2. 配对消息缺少完整的浏览器端排队边界（P2，页面可用性）

文件数据通道已有接收上限；加密协商 WebSocket 原来没有在 JSON 解析和解密之前限制消息大小或积压数量。异常、自定义或被入侵的配对服务可以不断排入消息，拖慢页面并增加内存占用。多人分享的状态 WebSocket 原来只限制单条长度，没有限制待处理消息的总量。

正式配对 Worker 已有消息大小和速率限制，因此不是正常用户发送文件即可突破服务端限制的证据，也没有发现攻击已经发生。本次补足浏览器信任边界：即使配对服务异常，前端仍应限制工作量。

修复保留正常的配对与重连格式。加密协商单条上限为 128,000 个字符，多人状态单条上限仍为 16,384 个字符；两个接收队列各自最多 128 条，待处理正文按 UTF-16 计最多 1 MiB。这里只约束应用层队列，不把它表述为整个浏览器的内存上限。

超限时断开异常配对连接并丢弃其待处理消息，不发送“结束分享”或“退出接收”，不主动关闭已建立的文件数据通道。新连接也受未完成消息的总量约束，避免靠反复重连绕过限制；旧连接正在解密的消息也会在分发前重新检查连接归属。

两条 WebSocket 路径都验证超长消息、积压条数、积压字节和非文本消息，并确认队列释放后计数归零、没有错误地发送结束分享命令。修改前积压场景可排入 5,000 条等待任务；修复后在边界处断开，未开始的任务不再进入业务处理。

另补充浏览器 WebSocket 检查：超限时使用客户端允许的私有关闭码 `4009`，确认关闭事件、提示和页面错误状态。此项在 Chromium 与 WebKit 实际执行，避免只靠简化的连接模拟漏掉浏览器 API 限制。

## 3. 仅配对连接中断，也会重建健康的文件直连（P2）

此前收到配对服务的 `peer-left` 通知就请求恢复，即使双方的数据通道仍开放、DTLS/SCTP 传输完全正常。真实测试只关闭接收方配对 WebSocket，就观察到额外创建一次 PeerConnection，导致本来正常的传输暂停、恢复和可能重发尚未确认的字节。这与“配对服务断开后，已建立直传可以继续”的预期不符。

修复后，该通知先检查数据通道和传输状态；健康直连继续运行。数据通道关闭、连接失败或断开时仍立即恢复，实际数据停止响应时由既有心跳启动恢复，不取消断点续传能力。这也保证第 2 项主动断开异常配对连接时，不会仅因服务通知就重建正常文件通道。

回归分别覆盖发送端和接收端的健康、通道关闭、传输失败状态；真实 16 MiB 传输期间断开接收方配对连接，验证双方只使用原来的一次 PeerConnection、发送字节没有增加、下载内容的独立 SHA-256 与原件一致。
