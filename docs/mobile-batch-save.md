# iPhone 多文件保存 · 2026-10-13

## 问题

用户在 Mac 发出三张图片后，iPhone Safari 点击“下载全部”只下载第一张。旧实现一次点击内连续触发五个独立下载，之后间隔 1.1 秒发送下一组。它在 Chrome 测试中可用，但没有覆盖 iPhone Safari 对多次下载和用户手势的实际处理；网页也无法确认每一个下载是否被浏览器接受。

## 修复

- iPhone / iPad 上，浏览器支持文件级 Web Share 时，接收完毕后提前准备完整的一组原文件。用户点击“保存全部”的同一次手势内直接调用系统文件分享/保存面板；不会先等待磁盘读取而丢失点击手势。可以在系统面板选择“存储到文件”，图片也可使用系统提供的图片保存选项。
- 传给系统的是独立 File 对象，保留原文件名、MIME 类型和原始字节，没有重新编码图片、ZIP 或服务器上传。该接口仅提交 files，不混入网页链接或文字。
- 为控制准备时的额外资源占用，系统批量保存准备限于整组总计 64 MiB。此限制只适用于这项保存入口，不是文件传输大小限制。更大的批次、接口缺失、canShare 拒绝或系统调用失败会使用逐个确认路径；桌面 Safari 也使用逐个确认路径。
- 逐个确认窗口每次仅有一个原文件下载链接。用户点击并确认浏览器提示后，再点击下一个；应用不继续自动触发多个下载。按钮和文件名在当前下载默认动作结束后才更新，避免前一张图片被后一张覆盖。
- 取消系统面板不会自动开始回退下载，也不标记已保存。系统成功返回只表示文件交给系统，不证明每个目标文件已经保存完成。清理暂存前仍需确认系统保存完成。
- 取消、重置、清理、到期或当前文件列表变化会使旧准备任务/保存队列失效；旧系统调用迟返回也不会在新会话显示保存标记。保存操作续期暂存，既有 10 分钟保留规则继续适用。
- 桌面 Chrome / Edge 保留既有批量下载方式；每个原文件的单独保存按钮始终可用。中英文说明同步更新。

## 验证

Chrome 专项覆盖真实 WebRTC 接收三张有效 PNG（磁盘和内存两种模式），检查交给系统的三份文件名、类型、字节摘要，并确认只进行一次、具有有效用户手势的系统调用。另测系统接口缺失、权限错误、取消和旧保存操作迟完成，以及逐个点击时三个下载的原文件名与字节一致性。

独立 WebKit 验证相同浏览器控制器中的真实点击手势、三个逐个下载、较大批次不预读文件、准备时取消、关闭后重新打开和迟完成隔离。完整回归保留普通下载、多文件、大文件、暂存、扫码、多人连接和续传检查。

**系统分享/保存面板在自动化中由测试接口替代；独立 WebKit 不是一台真实 iPhone。实际 iPhone Safari 的系统面板选项和保存落地仍需手机验证。**不会把这些结果说成已在 iPhone 上确认三张图片均保存。

参考：[W3C Web Share 规范](https://www.w3.org/TR/web-share/)，系统调用需要临时用户激活；canShare 检测可提前进行。测试命令为 `npm test` 和 `npm run test:webkit`，发布流程均会执行。

## 单个文件系统保存 · 2026-10-13

用户已确认 iPhone Safari 的“保存全部”成功弹出系统面板，可选择相册、文件和分享给其他 App。本次将同一能力接入当前传输和历史暂存的单个保存按钮，也覆盖只接收一个文件的场景。

- 仅提交选中的一个原始 File，原名、MIME 类型和字节保持一致。调用前已准备好文件，同一次点击同步调用 share，不等待磁盘读取。
- 单个与批量路径复用准备好的 File，不重复预读。当前传输优先，历史暂存随后；准备池合计最多 64 MiB。大文件或准备池没有容纳的文件保留直接下载，不增加传输大小限制。大批次中的小文件仍可单独使用系统面板。
- 取消系统面板不触发下载，不标记已保存；非取消错误提示再次点按，下一次手势才下载。文件交给系统后，状态提示确认实际保存结果，而非声称已经落地。
- 已移除或清理的文件不保留在准备池，迟到的读取和系统结果不能标记旧会话。历史暂存保存的反馈也在可见区域显示。

新增自动检查覆盖选择三张中的一张（磁盘和内存）、独立单文件接收、刷新后的历史暂存、共享准备避免重复读取、取消、权限失败后的再次点击下载、大批次内的小文件及旧系统结果隔离。独立 WebKit 也运行控制器检查。单个文件的真实 iPhone 系统保存仍需用户发布后复测。
