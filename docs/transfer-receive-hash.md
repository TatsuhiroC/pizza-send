# 接收端校验加速与发布构建对照 · 2026-10-17

后续审查与当前线上基线的整合结果，见[传输升级审查记录](transfer-upgrade-review.md)。本页保留首轮实现和验证数据。
本轮以当前公开版本 **`f897dfc`** 为最终基线。重建后的 `index-BGBrnzp2.js` 与实际公开网站脚本的 SHA-256 一致；候选保留了该版本的常亮开关、发送时间估算、原文件读取错误及扫码布局等修复。本轮改动保持本地，尚未推送或部署。

## 保留的改进与成本

接收端使用锁定为 `4.12.0` 的 [hash-wasm](https://github.com/Daninet/hash-wasm) 流式计算**同一个 SHA-256**。库随本站构建分发，不使用 CDN，也不上传文件。初始化不可用时回退到原有 `@noble/hashes` 实现。继续逐块校验，不把整个文件读入内存；恢复连接时保留接收校验对象。

发送端保留原有 JS 校验、最多 32 KiB 的顺序读取及续传检查点，并使用当前公开版的 `readSource` 及源文件错误通知。此前本地 `8c36fac` 的自动窗口、密集到达时合并写盘和按累计字节确认继续保留。DTLS、信令加密、协议版本、原文件名、原始字节、未确认量上限及暂存期限没有改变。

本轮也试过同时加速发送端、缩小网络消息、改变启动窗口及短暂预热，但较快的发送循环在重复对照中伴随长停顿和高延迟场景回退。这些改动全部撤回，没有把单次较好结果作为保留依据；底层停顿原因尚未完全确定。

成本：主脚本 gzip 从当前公开版 **62.57 kB** 增至 **71.11 kB**，约增加 **8.54 kB**。新增依赖与 WASM 属于需要信任的本站供应链代码。CSP 增加专门的 `wasm-unsafe-eval`，仍禁止字符串执行和非白名单脚本，详见[安全策略说明](web-security-headers.md)。没有新增文件中继、压缩步骤或付费服务。

## 对照方法

- macOS 27.0.1、Chrome 155.0.8059.80、Node 22.14.0，同一台机器，真实本地 WebRTC 和 OPFS。
- 使用各自的 **Vite 发布构建及安全响应头**。发送与接收处于独立浏览器环境；接收端用新建的普通持久测试配置（`BENCH_PERSISTENT=1`），测试后删除，避免隐私模式内存文件系统影响落盘验证。
- 每轮交替旧版／候选，隔轮反转先后顺序。文件从实际磁盘路径选择；较大文件采用小块生成，避免测试器自己持有整文件内存。
- 主计时从接收端发出 `accept` 到发出 `complete`，包括校验、落盘和结束处理，不包括页面加载、配对或下载后的独立校验。
- 每次实际下载，流式计算独立 Node SHA-256，与生成文件时的预期值比较，同时检查文件名及最多 4 MiB 未确认量。
- 回执延迟只推迟应用 ACK，**不是完整 WAN 模型**。CPU 4 倍限速只配置到接收目标，是 Chrome 合成条件，不代表某一型号手机。慢写盘模型按字节数计算服务时间，不按调用次数收取固定延迟。

## 最终对照结果

前五组每版本 3 次取中位数；1 GiB 为每版本 1 次，只用于大文件正确性及耗时参考。

| 场景 | 当前公开版 | 候选 | 判断 |
| --- | ---: | ---: | --- |
| 128 MiB，普通连接 | 5.168 秒 | 5.193 秒 | 基本持平 |
| 128 MiB，额外 ACK 延迟 150 ms | 5.303 秒 | 5.305 秒 | 基本持平 |
| 128 MiB，额外 ACK 延迟 300 ms | 10.108 秒 | 10.063 秒 | 基本持平 |
| 64 MiB，接收 CPU 4 倍限速 | 7.515 秒 | 2.798 秒 | 在此合成条件下耗时减少约 63% |
| 32 MiB，写盘服务按 8 MiB/s 限速 | 5.209 秒 | 4.789 秒 | 在此合成条件下耗时减少约 8% |
| 1 GiB，普通连接 | 40.825 秒 | 40.224 秒 | 两版均成功，单次结果不能证明固定提速 |

普通／延迟组接收页面的 CDP `TaskDuration` 中位数从 **3.085 秒降到 1.131 秒**，约减少 63%。这是页面主线程任务耗时，包含校验和其他页面工作，不是纯 SHA 耗时、整个浏览器 CPU 或电池消耗。总耗时仍受发送端、网络和写盘等瓶颈约束，不能因此宣称所有传输快 63%。

CPU 受限组旧版三次为 7.275、7.515、7.541 秒，候选为 2.856、2.702、2.798 秒。300 ms 延迟组候选范围为 10.057–10.280 秒，旧版为 10.053–10.118 秒；保留较慢轮次，不只挑中位数或最快结果。结论是**接收效率升级，较慢接收设备存在明确的本地模拟收益；普通连接没有证据证明普遍变快**。

最终共 **35 次成功对照传输**，包括新旧页面混用的两个方向和强制禁用 WASM 的回退；每次下载后的原文件名和独立 SHA-256 均通过。原始逐次摘要见[验证记录](archive/benchmarks/2026-10-17-receive-hash.json)，完整轨迹留在本机 `outputs/pizza-send-throughput-verification/receive-hash-2026-10-17/`。

## 早期诊断的边界

早期曾以 `b25e218` 对照；核对线上发现已更新到 `f897dfc` 后，保留既有记录，重新构建基线并完整补跑上述 35 次，未混算两组结果。

默认隐私上下文中，1 GiB 旧版多次报告 `No write progress`，网站显示“浏览器写盘失败”；存储估计额度为 10 GiB，并未保证实际写入成功。Chromium 的[文件系统说明](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/storage/browser/file_system/README.md)区分了隐私模式内存后端与普通配置磁盘后端。这些失败不能算作新版提速或修复线上故障的证明，其更底层成因未完全确定。改用普通配置后，两版均完成 1 GiB 写入、实际下载及独立校验。本轮没有为此引入猜测性的写盘重试。

## 功能验证

构建与配对 Worker dry-run 通过。Chromium 完整回归 **175 项通过**；独立 WebKit **30 项通过、3 项按设计跳过**；发布构建安全策略 **9 项通过、1 项按设计跳过**。合计 **214 项通过、4 项跳过**，最终记录没有未解决失败或不稳定重试项；35 次速度／兼容性对照另行记录，不重复计入这些功能检查。

覆盖多次断线和信令中断后的多文件续传、丢失最终完成回执、恢复后的损坏拦截、后台返回、多人独立收发、取消、磁盘故障、256 MiB 内存回退、200 MiB／1 GiB 原生写入及 512 MiB 暂存写入、原文件名／类型和手机保存面板。新校验器在 Chromium 与 WebKit 中连续处理 **4 GiB + 17 字节**，以有界输入缓冲得到与独立 Node SHA-256 相同的结果；同时检查不支持 WASM 时的 JS 回退、并发状态隔离及初始化期间取消后的文件清理。

安全专项验证真实发布构建的磁盘 Worker、WASM、配对和原文件下载。首轮新增的字符串执行检查直接在自动化求值环境中运行，无法代表普通页面权限；修正为由网页正常加载同源测试脚本后，两种引擎均确认 WASM 可执行、字符串执行及其他非授权脚本被阻止。未为此继续放宽 CSP，首轮诊断记录仍保留。

检查产物为本机 `/tmp/pizzasend-receive-hash-full`、`/tmp/pizzasend-receive-hash-webkit` 和 `/tmp/pizzasend-receive-hash-headers-final`。四项跳过均为当前独立 WebKit 自动化不覆盖的真实 WebRTC 场景，未将跳过计为通过。

真实 iPhone、Mac Safari、跨地区网络及真实 VPN 开关没有在本轮完成新的实机速度对照。先前已有的容量或 VPN 成功记录不能替代本轮的速度比较。超过 4 GiB 的校验检查仅证明增量校验计数正确，不等于完成 10／20 GiB 的网络传输测试。

## 复现

独立检出 `f897dfc`，安装相同依赖并构建，保留其 `dist` 不变，再构建候选。把下面的路径替换为自己的基线构建路径：

```sh
BENCH_BUILT=1 BENCH_PERSISTENT=1 BENCH_BASELINE_DIST=/tmp/baseline/dist BENCH_MIB=128 BENCH_REPEATS=3 npm run bench:latency
BENCH_BUILT=1 BENCH_PERSISTENT=1 BENCH_BASELINE_DIST=/tmp/baseline/dist BENCH_MIB=64 BENCH_DELAYS=0 BENCH_RECEIVER_CPU=4 npm run bench:latency
BENCH_BUILT=1 BENCH_PERSISTENT=1 BENCH_BASELINE_DIST=/tmp/baseline/dist BENCH_MIB=32 BENCH_DELAYS=0 BENCH_WRITE_MIBPS=8 npm run bench:latency
```

`BENCHMARK_RESULT` 指定原始 JSON 输出；`BENCH_VARIANTS` 可选择单独诊断某构建，`BENCH_RECEIVER_VARIANT` 检查新旧页面混用，`BENCH_DISABLE_WASM=1` 强制接收回退。`BENCH_PROFILE=1` 只用于 CPU 定位，不把启用采样剖析时的耗时作为速度对照。基准不进入产品构建，默认 CI 不把硬件测速当成功能门槛。
