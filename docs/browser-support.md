# 浏览器支持与扫码

本文描述当前主分支。正式站使用固定提交，测试站跟随主分支，见[版本隔离](test-site.md)。优先支持主流 Chrome / Edge、安卓 Chromium 和 iPhone / iPad / Mac Safari；不承诺兼容过去十年的全部浏览器。

构建语法目标为 Chrome 119、Safari 15.6。这是代码生成边界，不等于每款历史设备均已真机认证。程序按实际能力检测，不只按版本号判断。

| 能力 | 条件 | 不满足时 |
| --- | --- | --- |
| 自动分享与加密转发 | HTTPS、Web Crypto、WebSocket、基本文件与流接口 | 提示更换浏览器并保留邀请，不降为明文 |
| 直连 | 能创建 WebRTC DataChannel，且网络允许建立连接 | 双方认证协商加密转发，禁用不可用的直连选项 |
| 大文件暂存 | Worker、OPFS、Web Locks，以及实际写入和快照读回成功 | 总计最多 256 MiB 的内存接收 |
| 空间预估 | `StorageManager.estimate()` 可用 | 跳过辅助预估，仍处理实际写盘错误 |
| 可选压缩 | 双方支持 CompressionStream / DecompressionStream | 原样传输；手动配对缺少压缩接口时给出提示 |
| 系统保存、相机、剪贴板、常亮 | 对应接口、权限及用户手势 | 使用普通下载、图片识别或手动复制等既有退路 |
| 动画与布局观察器 | 对应可选接口可用 | 保留静态布局，不阻断传输 |

旧 Safari 可能返回异步暂存控制结果，程序等待 `flush / close / truncate / getSize`；额度查询缺失时不应直接阻断接收。依据：[Safari 16.4](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/)、[WebKit 存储策略](https://webkit.org/blog/14403/updates-to-storage-policy/)。

## 扫码

按可识别名称选择普通后置镜头；首次授权前名称不可见时，授权后再枚举。只把最终视频流接到预览，不循环试镜头，不在播放中反复改变采集尺寸或变焦。无法识别时保留系统选择，不能保证网页能锁定具体物理镜头。

iPhone 的原生视频显示曾出现尺寸不变但画面放大的问题。移动 Apple WebKit 采用同一视频流的完整帧绘制作为预览，最多 30 fps、最长边 960 像素；不是等画面稳定再显示。扫码框跟随实际比例，不用裁切填满画面；桌面保留原生视频。关闭、取消、成功或后台暂停均释放相机，异步旧回调不能影响新会话。

二维码识别只在本机进行。扫描成功后显示反馈并滚动到连接状态；完整邀请在文件列表到达前保留，避免浏览器交接后变为空接收页。

## 验证边界

Chrome / WebKit 自动检查覆盖接口缺失、接口拒绝、实际暂存、文件导出、无 WebRTC 加密转发、相机帧和邀请导航。历史 Safari 的特殊接口行为通过能力模拟检查；自动化 WebKit 不等于真实 iPhone。Chrome 119 的官方测试程序在当前 Mac 上无法启动，不能记为已验证。

`file://` 直接打开源码 HTML 无法执行 TypeScript，应使用开发服务器或 HTTPS 站点。微信域名拦截发生在页面加载之前，前端兼容修复不能解除平台拦截。
